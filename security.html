What Attest stores, reads and can't promise.

This page sets out how the app handles your data and where its protections stop. Statements about the app's behaviour were checked against its code and manifest.

How data is stored

Everything Attest keeps is held in Forge storage on Atlassian's infrastructure.

See the four kinds of record it keeps

Attest has no database of its own. There are four kinds of record.

RecordWhat it holds
Per pageApproval state, page version, a revision counter, owner and submitter account ids, approval and review dates, the date of the last reminder, when the record last changed, the content fingerprint, the lock outcome, the page's previous edit restrictions while it's locked (account ids and group names), and the signatures (account id, display name, role, UTC time, version, fingerprint, signing statement)
Per spaceApprovers (account id, display name, role), quorum, review period, locking preference, whether self-approval is allowed
Audit trailActing account id and display name, page, space, version, states before and after, UTC time, any note, sequence number and chain hashes
Privacy registerWhich account ids appear on which pages, and each account's display name, so closed accounts can be found and erased

The stored snapshot of a page's previous restrictions is never sent to the browser. The privacy policy lists every field.

No servers, no outside calls

Attest has no servers of its own, and its code makes requests to Confluence and nothing else.

What the manifest declares and what reaches the logs

Its manifest declares no outside network permissions, no remote services and no web triggers. Its code makes requests to Confluence and nothing else, and it contains no analytics, tracking or advertising components.

Attest is built to meet Atlassian's Runs on Atlassian requirements. It isn't listed on the Marketplace yet, so it doesn't display that badge today.

Errors go to Forge's logs. Those lines carry ids, HTTP statuses and, in a few diagnostic cases, request details or short extracts of a Confluence error response. Attest doesn't write page titles or bodies to its logs. We can see the logs from a customer site only if that site shares them.

Permission scopes

Attest asks for eleven permissions, and two of them are broader than the app needs.

See each permission and why it's there

The note under the table explains why those two are there.

ScopeWhy Attest needs it
storage:appTo keep the page records, space settings and audit trail in Forge storage
read:page:confluenceTo read a page's version, owner and last editor, and its title and body for the fingerprint
read:space:confluenceTo look up a space and check whether the person asking administers it
read:content.restriction:confluenceTo read a page's existing restrictions before changing them
write:content.restriction:confluenceTo apply the edit lock and restore the previous restrictions
read:confluence-content.allConfluence's older restriction endpoints, the only ones that can write restrictions, are gated on this scope
write:confluence-contentThe same restriction endpoints require this scope to write
read:confluence-content.summaryRequired to subscribe to the page-updated event that drives the automatic reset
read:confluence-userTo read display names for the record, and the app's own account id, which Confluence requires in any restriction set the app writes
write:comment:confluenceTo post the notices that Confluence turns into notifications
report:personal-dataTo report the accounts Attest holds data for, as Atlassian requires, and learn when one has closed

A note on the two broad scopes. read:confluence-content.all and write:confluence-content are broad enough to read and change content. Attest needs them because of how Confluence gates its restriction endpoints. In the code, the only things the app writes to Confluence are edit restrictions and page comments. No call changes a page's title or body.

What the app reads and keeps

Attest reads a page's title and body to compute a fingerprint, and keeps only the fingerprint.

See every read, when it happens and what stays

Most reads use the app's own access.

Attest readsWhenWhat it keeps
Page title and bodyOn submit, on approve, and when an approved document is viewedOnly the SHA-256 fingerprint. A fingerprint can't be turned back into the text.
Page version, owner and last editorWhen the panel, macro or a trigger needs themVersion and owner on the record. Who published a new version is named in the audit note when a reset happens.
Edit restrictionsWhen lockingA snapshot while locked, kept until it has been restored
View restrictionsWhenever edit restrictions are writtenNothing. They're sent back unchanged.
Display namesWhen recording an actionThe name, in the signature or audit entry
Whether a person administers a spaceWhen saving settings or exportingNothing

Two checks run as the signed-in person: whether they can read the page, and whether they administer the space. Because of that, Confluence may show an Allow access prompt the first time someone uses the app. Because the app reads with its own access, a page whose view restrictions leave Attest out can't be fingerprinted. The panel says so, and you decide whether to add it.

When an account closes

Attest reports the accounts it holds data for to Atlassian every week, as Atlassian's privacy guidelines require.

How erasure works and how it was tested

When an account has closed, Attest removes that person's id and name from page records, audit entries and approver lists. A signature stays, marked "Erased account", so the record of how many people signed survives.

This is the only edit the audit trail ever receives. An entry changed this way is marked redacted. It still links to the entries around it, but its contents can't be verified, so both the panel and the script count it separately and never as verified. This has been tested on the live platform with simulated accounts, not a real closed account.

Retention after uninstall

Records stay in Forge storage for as long as the app is installed.

What happens after uninstall, and what to do first

When it's uninstalled, Atlassian keeps the app's data for 28 days. It can be recovered if requested within 21 days, and after that it's gone, including the audit trail. Export the trail before uninstalling.

Page content and page history aren't affected, because they belong to Confluence and Attest doesn't hold a copy. Two things need attention before you remove the app. Attest has no uninstall step, so an edit lock on an approved page stays in place as an ordinary Confluence restriction until someone changes it. The Approval signatures macro needs the app to render, so pages that use it will show a Confluence error in its place.

Tamper evidence and its limits

The audit code has no way for anyone to edit or delete an entry, and a hash check reveals some later changes and misses others.

What a check shows, and what it won't

What the app does. Each entry's hash covers all its fields and the previous entry's hash. Writes are conditional, so two simultaneous writers can't claim the same place in the chain, and a losing writer re-reads and retries.

What a check will show. Changing an entry, or removing one from the middle or the start of a chain, breaks the chain. The panel and the independent script both report it. Entries marked redacted are counted separately and never as verified.

What a check won't show. The hashes aren't keyed, so someone able to rewrite the app's storage could recompute every hash after their change. A redacted entry's contents can't be verified at all, so someone with that access, or anyone editing an exported file, could also present a change as a redaction. A redacted count you didn't expect is worth asking about. Removing the newest entries leaves a valid shorter chain, which only shows if you kept an earlier newest hash. And a compromised space administrator is a compromised approval chain, because they control who approves. Their settings changes still go on the trail.

What to do about it. Keep the newest hash from each export somewhere outside Confluence, and check that it still appears in later exports. A rewrite can't match a hash you hold.

What it doesn't do for compliance

Attest doesn't make you compliant with anything.

What it isn't, and what it leaves out

It isn't 21 CFR Part 11 compliant or ISO 13485 certified, and no software vendor can deliver either. You validate your own process, and Attest gives you approval records you can hand to an auditor as part of that.

  • There's no re-authentication at signing, because Forge has no way to ask Confluence for it.
  • There's no content snapshot. Confluence's page history holds the content.
  • The fingerprint doesn't cover attachments or content included from other pages.
  • There's no validation package.
  • Roles are text typed by a space administrator, and Attest doesn't check them against anything else.
  • Attest hasn't been through a real audit.

What has been tested

Attest has run live on a real Confluence Cloud site, from 4 to 6 November 2026, with two real accounts.

See what ran live and what hasn't

Run live on a real Confluence Cloud site, 4 to 6 November 2026:

  • The reminder comment, then expiry and release of the lock
  • Server refusal when a page changes mid-signing
  • Server refusal of a non-approver, and of a submitter or last editor approving their own version, using a panel left open after the permission was withdrawn
  • A role change recorded in the audit trail
  • A downloaded PDF of an approved page carrying the full signature record, and the Word export's contents checked for the same record. The Word file hasn't been opened in Microsoft Word
  • Send-back and submission notices
  • View restrictions preserved through lock and reset
  • Two signatures written at the same moment both kept, in a storage test on the live platform using simulated accounts
  • The independent script verifying a real export, and failing it when one value was changed
  • A non-admin opening the space settings: Confluence refused them, so the settings never loaded
  • Separation of duties with two people: the submitter had no Approve button and the other person signed
  • A quorum of two: the page stayed In review after the first signature and was approved after a second person signed
  • A direct save by someone who isn't an approver, on an approved page: refused, and the page didn't change. Publishing a new version then reset the approval and gave them edit access again

Covered by unit tests, not yet run live: Attest's own admin check on saving settings. In the live test Confluence refused the non-admin first, so that check wasn't reached.

Not yet tested: an install by an administrator outside our own test site.
